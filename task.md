# TermLinux — техническое задание

## 1. Цель проекта

Создать самостоятельное Android-приложение **TermLinux**, которое устанавливает и запускает полноценное пользовательское окружение Linux через PRoot без необходимости устанавливать Termux, получать root-доступ или поднимать SSH-сервер.

После первичной настройки пользователь должен попадать непосредственно в интерактивный Linux-терминал. Приложение должно поддерживать физическую клавиатуру и мышь, работу Linux-сессии при сворачивании приложения и доступ Linux к общей памяти телефона по пути `/sdcard` — в пределах разрешений, предоставленных Android.

**Целевые устройства:** Android ARM64, в частности Samsung Galaxy S22+ на Android 16.

## 2. Основные требования

- Не требовать root, Termux, BusyBox, стороннего Linux-приложения или SSH.
- Поддерживать ARM64 (aarch64).
- При первом запуске предлагать выбрать дистрибутив: Debian, Ubuntu или Alpine.
- Самостоятельно загружать, проверять и устанавливать rootfs.
- После установки открывать настоящий интерактивный shell.
- Обеспечить доступ Linux к общей памяти Android по пути `/sdcard`, если пользователь предоставил нужное разрешение.
- Поддерживать физическую клавиатуру, мышь, терминальные ANSI/VT-последовательности.
- По возможности сохранять работающую сессию при сворачивании Activity.
- Не показывать ложные сообщения об успешном восстановлении процесса, если Android уже завершил его.

## 3. UX и сценарии

### Первый запуск

1. Показать краткое описание возможностей и ограничений доступа к файлам Android.
2. Предложить Debian, Ubuntu или Alpine.
3. Предложить настроить доступ к общей памяти:
   - основной вариант — запросить у пользователя доступ к общей памяти Android через поддерживаемый системой механизм;
   - если доступ ко всем файлам недоступен или не разрешён, предложить выбрать папку через системный Storage Access Framework (SAF);
   - объяснить, что без разрешения Linux не сможет свободно читать и изменять все файлы телефона.
4. Скачать rootfs и необходимые компоненты.
5. Проверить контрольные суммы и безопасно распаковать rootfs.
6. Запустить shell.

### Обычный запуск

- Если дистрибутив установлен — сразу открывать терминал.
- Если установка не завершена — предложить безопасно продолжить или повторить её.
- Не запускать повторную установку поверх исправного rootfs без подтверждения.

### Терминальный экран

- Почти весь экран занимает терминал.
- Нет постоянно отображаемой панели инструментов.
- Настройки и выход из терминального режима доступны через заданный жест.
- Системные панели Android скрываются в immersive-режиме, но приложение не должно пытаться обходить системные ограничения навигации.

## 8. Доступ к памяти Android: `/sdcard`

Это обязательная функция проекта. В Linux-окружении пользователь должен иметь понятный путь `/sdcard`, ведущий к общей памяти телефона (обычно это содержимое Android shared storage, соответствующее `/storage/emulated/0`).

### 8.1 Целевое поведение

При наличии достаточных разрешений:

```bash
ls /sdcard
cd /sdcard/Download
```

Пользователь должен иметь возможность просматривать, читать и создавать файлы в пределах разрешённой Android общей памяти. По возможности также создать удобную ссылку:

```text
/storage/emulated/0 -> /sdcard
```

Не обещать доступ к закрытым каталогам других приложений, приватным данным приложений или системным разделам Android.

### 8.2 Важные ограничения Android

- PRoot сам по себе не предоставляет приложению дополнительных Android-разрешений.
- Наличие каталога `/sdcard` внутри rootfs не означает, что он реально подключён к памяти телефона.
- На современных версиях Android обычные старые разрешения `READ_EXTERNAL_STORAGE`/`WRITE_EXTERNAL_STORAGE` не дают универсального доступа ко всем файлам.
- `MANAGE_EXTERNAL_STORAGE` — специальный доступ «ко всем файлам». Его можно использовать только если приложение соответствует требованиям конкретной версии Android и правилам распространения приложения. Не считать, что Google Play автоматически разрешит его.
- SAF предоставляет доступ к выбранным пользователем файлам/папкам, но URI от SAF не является обычным POSIX-путём и его нельзя напрямую передать в PRoot как путь для bind mount.
- Не использовать скрытые API, обход scoped storage, root-хаки или уязвимости Android.

### 8.3 Два режима Storage Bridge

Реализовать единый `StorageBridge` с двумя режимами.

**Режим A — прямой доступ к общей памяти (если Android разрешил):**

1. Проверить состояние специального разрешения `MANAGE_EXTERNAL_STORAGE` через публичные Android API.
2. Если оно допустимо для данного варианта распространения приложения, объяснить пользователю назначение доступа и открыть системный экран настроек для его выдачи.
3. После возвращения в приложение повторно проверить разрешение.
4. Проверить доступность реального пути общей памяти, обычно `/storage/emulated/0`.
5. Создать точку подключения `/sdcard` в Linux rootfs и выполнить PRoot bind mount реального пути общей памяти в `/sdcard`.
6. Если путь недоступен или bind не сработал, показать понятную ошибку и не выдавать фиктивный результат.
7. Не запрашивать разрешение неожиданно: объяснить, зачем оно нужно, и дать возможность продолжить без него.

Пример концептуальной команды PRoot (конкретный синтаксис сверить с используемой сборкой PRoot):

```bash
proot \
  --bind=/storage/emulated/0:/sdcard \
  --rootfs=/path/to/rootfs \
  /usr/bin/env -i HOME=/root TERM=xterm-256color /bin/bash -l
```

Это пример архитектурной идеи, а не готовая команда для копирования. Реальную команду собирать аргументами безопасно, не конкатенировать пользовательские строки в shell-команду.

**Режим B — SAF, ограниченный выбранной папкой:**

1. Если прямой доступ недоступен, дать пользователю выбрать папку через `ACTION_OPEN_DOCUMENT_TREE`.
2. Запросить persistable URI permission и сохранить URI через DataStore.
3. После перезапуска проверить, что разрешение всё ещё действительно.
4. Не пытаться использовать `content://` URI как обычный путь файловой системы.
5. Реализовать SAF-backed файловый интерфейс/операции через `ContentResolver` для просмотра, чтения, создания, записи, переименования и удаления поддерживаемых документов.
6. Сделать этот интерфейс доступным из Linux через отдельный Storage Bridge. Предпочтительный первый безопасный вариант — Linux-команды/утилита `termux-storage`-подобного назначения, например `tlfiles`, общающаяся с Android-компонентом через локальный IPC/JNI и предоставляющая операции с выбранным деревом.
7. Если для полной прозрачности требуется обычный POSIX mount, исследовать отдельную совместимую реализацию userspace filesystem/FUSE. Не заявлять, что SAF URI можно просто bind-mount-нуть. Если полноценный POSIX mount не реализован, честно обозначить SAF-режим как ограниченный файловый мост, а не как полный `/sdcard`.

### 8.4 Поведение пути `/sdcard`

- В режиме A `/sdcard` должен быть реальным bind mount общей памяти.
- В режиме B создать `/sdcard` как точку входа в Linux Storage Bridge и явно документировать ограничения реализации. Если прозрачный POSIX-интерфейс не готов, не создавать пустой каталог, который выглядит как рабочая память телефона.
- При отсутствии обоих разрешённых режимов сообщить, что доступ к памяти не настроен, и показать способ настройки.
- В Linux добавить понятную справку, например `termux-storage-setup` или `tlfiles help`.
- Не выдавать доступ к приватным каталогам приложения Android и другим закрытым данным.
- Проверить чтение/запись файлов с пробелами, кириллицей, emoji и длинными именами.
- Проверить поведение при отключении разрешения во время работы и при повторном запуске.
- Учитывать, что некоторые файловые операции и Unix-права на общей памяти Android ограничены самой Android/FUSE-реализацией.

### 8.5 Проверки `/sdcard`

В режиме прямого доступа:
```bash
ls -la /sdcard
ls /sdcard/Download
printf 'TermLinux test\n' > /sdcard/Download/termlinux-test.txt
cat /sdcard/Download/termlinux-test.txt
```

Затем проверить наличие созданного файла в Android-файловом менеджере и удалить тестовый файл.

В режиме SAF проверить все операции, реально реализованные мостом, и явно отметить неподдерживаемые POSIX-функции.

## 13. Жест выхода из терминального режима

Жест: **три пальца одновременно, три последовательных касания**.

- Одно касание засчитывается только если одновременно распознаны три активных указателя.
- После каждого касания все три пальца должны быть отпущены.
- Для выхода нужны три отдельных завершённых касания.
- Между касаниями действует разумный таймаут; при превышении счётчик сбрасывается.
- Любое неоднозначное событие сбрасывает или не увеличивает счётчик.
- Жест не должен посылать сигнал завершения shell и не должен убивать Linux-процессы.
- Учитывать ограничения Android по доставке multi-touch событий и системным жестам.

## 14. Session Manager и фон

- Отвязать жизненный цикл Linux-процесса от Activity.
- Использовать Foreground Service, когда это разрешено Android и когда пользователь явно запускает длительную сессию.
- Показывать корректное системное уведомление о работающей сессии.
- При сворачивании Activity не закрывать PTY намеренно.
- При возвращении подключаться к существующей сессии.
- Поддержать несколько состояний: running, paused/interrupted, exited, failed.
- Сохранять scrollback и метаданные сессии по возможности.
- Не утверждать, что процесс переживёт принудительную остановку приложения, перезагрузку или завершение процесса ОС.
- При смерти процесса обнаруживать потерю сессии и честно сообщать об этом.
- Соблюдать ограничения Android 12+ и Android 14+ на запуск и типы foreground services.

## 15. Хранение данных

- Внутренние данные и временные файлы не должны быть доступны другим приложениям.
- Общая память подключается отдельно через Storage Bridge.
- SAF URI и разрешения хранить безопасно.
- Не сохранять секреты и токены в открытом виде.
- Экспорт/импорт конфигураций выполнять через SAF.

- `INTERNET` — загрузка rootfs и обновлений.
- `FOREGROUND_SERVICE` и подходящий тип foreground service — только согласно целевой версии Android и реальному сценарию.
- `POST_NOTIFICATIONS` — уведомление о длительной сессии на версиях Android, где оно требуется.
- SAF — через системный picker, без широкого разрешения на всё хранилище.
- `MANAGE_EXTERNAL_STORAGE` — только как необязательный режим прямого доступа, если приложение имеет право его использовать и пользователь явно включил его в настройках Android.

Не запрашивать старые storage permissions без понимания их поведения на целевых версиях Android. Не использовать Accessibility Service для обхода ограничений ввода или хранения.

## 17. Безопасность

- Только HTTPS для загрузок.
- SHA-256 и проверка целостности.
- Безопасная распаковка архивов.
- Проверка symlink/hardlink и путей.
- Не выполнять неподтверждённые скрипты из случайных источников.
- Не давать rootfs доступ к приватным данным приложения сверх необходимого.
- Не делать произвольные bind mounts по недоверенным путям.
- Не передавать пользовательский ввод через небезопасную shell-конкатенацию.
- Валидировать аргументы PRoot и пути.
- Логировать ошибки без утечки персональных данных.

## 21. Критерии готовности

Проект считается готовым к первой полноценной демонстрации, если:

1. Приложение устанавливается и запускается на ARM64 Android без root и Termux.
2. Пользователь может выбрать и установить Debian.
3. После установки открывается интерактивный Linux shell.
4. PTY и терминальный renderer работают стабильно.
5. Клавиатура и мышь поддерживают заявленные возможности.
6. При доступном Android-разрешении общая память телефона доступна в Linux по `/sdcard`.
7. Если прямой доступ запрещён, приложение предлагает SAF-режим и честно сообщает о его ограничениях.
8. Работающая сессия сохраняется при обычном сворачивании в рамках ограничений Android.
9. Жест выхода не завершает Linux-процессы.
10. Нет зависимости от Termux, root или SSH.

## 22. Правила для AI-агента-разработчика

- Сначала изучить существующий репозиторий и не перезаписывать рабочие файлы без необходимости.
- Перед выбором PRoot и terminal renderer проверить совместимость с Android ARM64 и лицензии.
- Начать с технического прототипа PRoot + PTY + `/sdcard`, а не с полировки интерфейса.
- Реализовывать проект по этапам, после каждого этапа собирать и тестировать приложение.
- Проверять работу на реальном Android-устройстве, а не только в эмуляторе.
- Не подменять реальные функции демонстрационными заглушками.
- Не утверждать, что `/sdcard` работает, пока не выполнены реальные тесты чтения и записи.
- Не считать SAF URI POSIX-путём и не пытаться bind mount-ить `content://` URI напрямую.
- Не обещать обход Android scoped storage или системных ограничений.
- Не обещать перехват системных клавиш, бессмертные фоновые процессы или полноценный Linux kernel.
- Не хардкодить непроверенные URL rootfs.
- Не блокировать UI сетевыми, файловыми или процессными операциями.
- Документировать все ограничения и известные проблемы.
